# 方案 A：手机 → 设备 → 屏幕（票据 / 截图投屏）

> 状态：**开发中（选定方案）**
> 目标场景：坐火车/飞机时，把 12306、航旅纵横、飞常准里的行程信息投到板子屏幕上，
> 抬手就能核对，不必反复开 App。

---

## 1. 需求拆解

| # | 需求 | 结论 |
|---|---|---|
| 1 | 手机把信息传给设备 | **BLE（主）+ HTTP（辅）**，BLE 不打断手机上网 |
| 2 | 设备保存，随时看 | 存 FFat（10 MB 分区），掉电不丢，可存多条翻页 |
| 3 | 屏幕常显 / 自动熄屏 | 显示 30 s 后熄屏，**IMU 敲击唤醒** |
| 4 | 支持 12306 火车票 | 文字路线：复制文本 / OCR；图片路线：截图裁剪 |
| 5 | 支持航旅纵横/飞常准 | 同上，无开放 API，一律走"手机侧取信息" |
| 6 | 文字 + 图片两条路线并存 | **同一套条目容器，两种负载类型** |

### 关键前提（已核实）
- **没有开放 API**：12306 / 航旅纵横 / 飞常准均不提供第三方接口；逆向需登录态与签名，易失效，不做。
- **动态二维码做不了**：加密且每次刷新，只能投文字/截图，不能当票据使用。
- **屏幕物理分辨率 = 320×240**（横向）：任何"高分辨率"都在这个上限内，投图的价值在"裁剪放大"而非提高像素。

---

## 2. 为什么选 BLE 而不是 Wi-Fi

| 传输方式 | 手机上网 | 跨平台 | 传输速度 | 结论 |
|---|---|---|---|---|
| SoftAP（设备开热点） | ❌ 手机断网 | ✅ 零安装 | 快（HTTP） | 仅作兜底 |
| 同局域网 HTTP | ✅ | ✅ | 快 | 家里/酒店可用 |
| **BLE（NUS）** | ✅ **不影响** | ✅ | 10–40 KB/s | **主通道** |

BLE 实测口径：MTU 247 + 短连接间隔 + 写无响应，可稳定 10–40 KB/s；20 KB 的 JPEG 约 0.5–2 s，完全够用。

## 3. 系统架构

```
手机                                ESP32-S3-LCD-2
┌──────────────┐   BLE NUS      ┌──────────────────────────┐
│ Android App  │ ──────────────▶│ BLE 服务（NimBLE）        │
│  · 剪贴板     │                │   ↓ 帧解析                │
│  · OCR       │                │ 条目存储（FFat /data/）    │
│  · 裁剪       │                │   ↓                       │
│  · JPEG 编码  │                │ UI 渲染（ST7789 320×240）  │
└──────────────┘                │ 电源管理（背光/睡屏/唤醒）  │
┌──────────────┐   BLE NUS      │                          │
│ iOS          │ ──────────────▶│                          │
│ nRF Toolbox  │  （仅文字）     │                          │
└──────────────┘                └──────────────────────────┘
```

### 客户端矩阵（现实约束）

| 平台 | 工具 | 能做到 | 限制 |
|---|---|---|---|
| Android | **自建 App**（Kotlin） | 文字 + 截图 + OCR + 裁剪 + BLE 传图，全功能 | 需要开发，Windows 上可完成 |
| Android | Serial Bluetooth Terminal | 发文字 | 无图 |
| iOS | **nRF Toolbox（UART）** | 发文字 | **iOS 快捷指令没有 BLE 写能力**，且 Windows 无法构建 iOS App；传图无零安装方案 |

> 结论：**文字路线双端都能用**；**图片路线只有 Android 自建 App 能做到**（或 iOS 借道 SoftAP 兜底）。
> 固件实现 **Nordic UART Service（NUS）** 的 UUID，好处是 nRF Toolbox 与 Serial Bluetooth Terminal 都能直接连上，零开发即可调试。

UUID：
```
Service  6E400001-B5A3-F393-E0A9-E50E24DCCA9E
RX(write)6E400002-B5A3-F393-E0A9-E50E24DCCA9E   ← 手机写入
TX(notify)6E400003-B5A3-F393-E0A9-E50E24DCCA9E  ← 设备回执
```

## 4. 通信协议（文本行头 + 可选二进制体）

所有指令以 ASCII 行形式下发，`\n` 结尾；二进制负载紧跟在头行之后。

### 4.1 文本条目
```
T {"title":"G1234 北京南→上海虹桥","sub":"11-02 08:00 - 12:30","lines":["05车 12F 靠窗","检票口 13A","二等座 ¥553"]}\n
```
- 最多 12 行，每行 40 字符；超出截断并提示。
- 设备回执：`OK 3\n`（3 = 条目索引）

### 4.2 图片条目
```
I 320 240 21430 jpeg\n
<21430 字节二进制>
```
- `w h size fmt`；`fmt ∈ {jpeg, mono}`（mono = 1-bit 二值图，见 §5.2）
- 设备回执：`OK 4\n`；失败 `ERR decode\n`

### 4.3 控制
```
L\n            列出条目（TX 通知回 JSON 索引）
P 3\n          切到第 3 条
D 3\n          删除第 3 条
C\n            清空
B 60\n         设置熄屏超时（秒），0 = 不熄屏
V\n            查询版本/电量/RSSI
```

### 4.4 回执格式
```
OK <arg> | ERR <reason>
```
超时 3 s 无回执 = 手机侧重发（最多 3 次）。

## 5. 截图路线（回答"能不能直接截屏发过去"）

**能，而且这是保真度最高的路线。** 但要明确三件事：

### 5.1 裁剪必须在手机端做
设备手里只有"已压缩的图"，没有原始截图，也不适合跑智能裁剪（算力/内存不划算）。
三种裁剪策略，按可靠性排序：

| 策略 | 做法 | 可靠性 | 实现成本 |
|---|---|---|---|
| **手动框选** | App 里拖动选框 | ★★★ 100% | 低 |
| **OCR 定位** | ML Kit / Vision 识别文字块 → 取外接矩形并留边 | ★★☆ 95% | 中 |
| **内容检测** | 找"非背景色"（白底/深底）连通区域 | ★★ 85% | 中 |

推荐：**手动框选为主，OCR 自动定位做"一键建议框"**，用户可微调。

### 5.2 分辨率：上限 320×240，优化在别处
- 屏幕就 320×240，传 1080p 是浪费带宽且必然缩糊。
- 真正提升可读性的是**裁剪**：把票面关键区域裁出来占满整屏，等效放大 3–5 倍。
- **额外优化（推荐）**：票面截图多为"白底黑字"，转成 **1-bit 二值图 + RLE / 或低质量 JPEG**，体积可从 30 KB 压到 **5–10 KB**，BLE 秒传，且在低像素屏上比彩色 JPEG 更锐利。

### 5.3 端到端耗时估算（Android + BLE）
```
截图       0 s（手机已有）
裁剪       1–2 s（手动）
压缩       0.1 s（Android 原生）
BLE 传输   0.3–1 s（10–20 KB @ 20–40 KB/s）
设备解码   0.05–0.1 s（TJpeg_Decoder，PSRAM 帧缓冲）
刷新屏幕   0.03 s（SPI 40 MHz）
```
合计约 2–4 秒，其中大头是人工裁剪。

## 6. 文字与图片能否并存

**能，而且是同一套机制**：条目 = `{type, title, payload}`。
- `type=text` → 渲染成卡片（大标题 + 正文行），省流量、可翻页、可搜索
- `type=img` → 渲染成整屏图（居中/铺满），保真
- 列表里两类混排，屏幕上按索引前后翻

存储布局（FFat，10 MB）：
```
/data/idx.json        条目索引（顺序、类型、标题、时间）
/data/t000.json       文本条目
/data/i000.jpg        图片条目
```
10 MB 可存约 **400 张 20 KB 截图** 或 **上千条文本**；可实现"滑出 50 条自动淘汰最旧"。

## 7. 屏幕与交互

| 项目 | 设计 |
|---|---|
| 横屏 | 320×240，ST7789T3 |
| 文本卡 | 顶部 24 px 标题条（深色底反白）+ 10 行 16 px 正文 |
| 图片 | 等比铺满，黑边填充 |
| 翻页 | **QMI8658 敲击/倾斜**（←→），或手机 App 下 `P n` 指令 |
| 熄屏 | 30 s 无操作 → 背光 PWM=0 + LCD `sleep in` |
| 唤醒 | **IMU 任意运动中断**（GPIO3） |

### 硬约束（已核实，见 `docs/引脚定义.md`）
- **GPIO0 = LCD_RST = BOOT**：按 BOOT 会顺带复位屏幕 → 唤醒后需重新 `tft.init()`（约 120 ms 黑屏）。
  因此**不用 BOOT 做唤醒**，改用 IMU 中断。
- **GPIO3 = LCD_TE = IMU_INT1**：二者只能选一个；本方案用 IMU 中断，放弃 TE 防撕裂（静态画面无影响）。

## 8. 功耗预算

| 状态 | 电流 | 2000 mAh 续航 |
|---|---|---|
| 亮屏 + BLE 连接 | 100–150 mA | ~12–15 h |
| 熄屏（LCD sleep + 背光 0）+ BLE 空闲 | 8–15 mA | **6–10 天** |
| 深睡（BLE 断开） | ~0.02 mA | 数月 |

设计取舍：**保留 BLE 常连（8–15 mA），换取"随时可收消息"**；出行场景下待机一周足够。

## 9. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| **M1**（今天） | BLE NUS 服务 + `T` 指令 + FFat 存 + 文本卡渲染 | 手机（nRF Toolbox）发一段文字，屏幕显示 |
| M2 | 多条目翻页 + `L/P/D/C` 指令 + 熄屏/IMU 唤醒 | 断电重启内容还在；敲击亮屏 |
| M3 | 图片路线：`I` 指令 + JPEG 解码 + 定点显示 | 传一张 320×240 JPEG 满屏显示 |
| M4 | Android App：粘贴/OCR/裁剪/发送 | 截图 → 3 秒内上屏 |
| M5 | 宽松解析：12306 / 航旅文本 → 结构化卡片 | 粘贴原文自动拆出车次/时间/座位/检票口 |

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| iOS 无 BLE 写能力 | iPhone 只能用 nRF Toolbox 发文字 | 图片路线限 Android；或 iOS 用 SoftAP 兜底 |
| BLE 传输慢（MTU 未协商） | 传图超时 | 连接后主动 `requestMtu(517)`；失败降到 mono 二值图（5 KB） |
| 票面文本格式变化 | 解析失败 | 永远保留"原文直显"回退，解析只是增强 |
| 屏幕 RST=BOOT 冲突 | 唤醒闪屏 | 已改 IMU 唤醒 |
| FFat 写坏/掉电 | 条目丢失 | 先写 `.tmp` 再 rename 原子替换 |
